1. Introduction
1.1 Purpose
This Software Requirements Specification (SRS) defines functional and non-functional requirements for the Kwickly platform — an on-demand home services application targeting Indian urban markets. It covers all three primary actors (Customer, Worker, Admin) across all three codebases.
1.2 Product Overview
Kwickly connects customers who need home repair and maintenance services with skilled local workers. The platform handles job booking, worker matching via expanding-radius broadcast, real-time GPS tracking, OTP-based arrival and completion verification, payment via UPI/QR (Razorpay), and platform revenue through commission splits.
1.3 Scope
Mobile-first application (iOS 15+ and Android 8+) targeting Indian urban markets
Three user roles: Customer (end user), Worker (service provider), Admin (platform operator)
Service categories: Plumbing, Electrical, Carpentry, AC Repair, Painting, Cleaning, Appliances, and more
Payments via UPI/QR (Razorpay) with automatic commission split
Worker subscription model: 90-day free trial, then monthly/semi-annual/annual plans
Worker wallet system: minimum Rs. 100 balance to receive job alerts
Dynamic admin panel: all platform parameters configurable at runtime, pushed live to all connected clients

3.3 Dynamic Configuration — AppSettings
Every configurable platform value is stored in a single MongoDB AppSettings singleton document. The mobile apps fetch this on every launch and cache it locally. When Admin changes any setting, the backend writes it to MongoDB and emits a settings_updated Socket.io event to all connected clients, which apply the change without app restart.

3.6 Redis Caching Strategy
Redis is introduced as a caching and ephemeral-data layer to eliminate repeated MongoDB reads for high-frequency, low-mutation data. MongoDB remains the source of truth for all persistent records; Redis serves as the fast-read layer. All cache writes are synchronous with the MongoDB write (write-through); cache misses fall back to MongoDB and repopulate the cache.

5.5 Dynamic Settings Sync Flow (Admin → Mobile)
#
Step
1
App Launch: Mobile app calls GET /api/app/settings on every launch; caches the full AppSettings document locally.
2
Admin Change: Admin saves a setting in the Admin Panel; backend writes the new value to MongoDB AppSettings document.
3
Real-Time Push: Backend emits a settings_updated Socket.io event to all connected mobile clients with the changed key and new value.
4
App Applies Change: Mobile app receives the event, updates local settings cache, re-renders affected UI components immediately — no restart needed.
5
Backend Re-reads: For every job operation (commission calculation, radius expansion, OTP validation, quote expiry), the backend reads AppSettings from MongoDB at runtime — disconnected devices always get updated values on their next server interaction.

14. Error States &amp; Edge Case Handling

14.1 Authentication Edge Cases
Scenario
System Behaviour
OTP expired (&gt; 5 min)
Entry blocked; error shown: 'OTP has expired. Please request a new one.' Resend button enabled immediately.
6 failed OTP attempts
Account temporarily locked for 30 minutes. Error: 'Too many failed attempts. Try again in 30 minutes.' Both OTP entry and resend disabled.
OTP resend before 30s cooldown
Resend button disabled with countdown timer. Request blocked server-side as well.
JWT expired mid-session
App silently attempts token refresh via POST /auth/refresh-token. On success: continue seamlessly. On failure: log user out and redirect to Login screen with message 'Session expired. Please log in again.'
Duplicate mobile registration
If mobile already exists in DB: OTP verification succeeds and user is directed to password login instead of registration.
Admin forces password reset
On next login attempt, user is shown a mandatory password change screen before accessing the app.

14.2 Booking &amp; Job Edge Cases
Scenario
System Behaviour
Connection lost during booking wizard
Wizard state saved to local draft. On reconnect, user can resume from where they left off. Submitted if user confirms on resume.
Worker goes offline after accepting job
Job remains ACCEPTED. Customer continues tracking (last known location shown). Worker must come back online and complete the job.
Arrival OTP entered incorrectly
Error shown: 'Incorrect OTP. Please check with the customer.' OTP attempt counted. After 6 failed attempts: Admin is notified; Customer can regenerate a new Arrival OTP.
Completion OTP entered incorrectly
Error shown: 'Incorrect OTP. Please check with the worker.' After 6 failed attempts: Admin is notified to intervene.
Customer cancels after worker en route
Cancel button is hidden once job reaches EN_ROUTE status. Customer must contact support. Admin can force-cancel from Job Management.
Worker does not arrive (timeout)
No automatic timeout in v1. Customer can raise a dispute from the active job screen. Admin intervenes via Job Management.
All quotes expire before acceptance
If all quotes expire and customer has not accepted any: job returns to PENDING state and radius broadcast is re-run from Round 1.
Category disabled mid-booking
If Admin disables a category while a customer is mid-wizard: wizard completes and job is submitted. The disable only affects new bookings started after the change.

14.3 Payment Edge Cases
Scenario
System Behaviour
QR code expires (10 min)
Countdown reaches zero; QR is invalidated. Customer sees 'QR expired — generate a new one' with a Regenerate button. New QR valid for another 10 minutes.
Razorpay webhook delayed
Payment shown as PENDING on customer screen. Razorpay webhook retries for up to 24 hours. Admin can manually confirm from Payment Management if needed.
Double payment attempt
Server enforces idempotency via razorpay_ref. Duplicate payment detected; second transaction blocked; customer refunded automatically by Razorpay.
Cash payment selected
Worker earnings are credited manually by Admin (or via a deferred auto-credit after admin audit) since no Razorpay event fires for cash jobs.
Commission rate changed mid-job
Commission is locked at the rate active when the job was accepted. Admin setting changes only apply to newly accepted jobs.

14.4 Worker Wallet Edge Cases
Scenario
System Behaviour
Balance drops below Rs.100 mid-job
Worker can complete their current active job. The minimum balance check only gates receiving NEW job alerts. Pausing applies immediately after the current job closes.
Top-up payment fails
Wallet not credited. Error shown with retry option. Razorpay order remains open for 15 minutes for retry.
Trial expires mid-active job
Active job is unaffected and completes normally. After completion, wallet minimum is enforced for subsequent job alerts.
Admin credits wallet while worker is active
Credit applied immediately; balance updates in real-time; if balance crosses Rs.100, job alerts resume instantly without any action from the worker.

15. Security Architecture

15.1 Authentication &amp; Token Management
Component
Implementation
Mobile JWT
Issued on login; stored in device secure storage (iOS Keychain / Android Keystore); sent as Authorization: Bearer header on every API call
Admin JWT
Issued on admin login; stored in httpOnly cookie (not accessible via JS); 7-day expiry with refresh token rotation
Token Refresh
POST /auth/refresh-token uses a short-lived refresh token stored separately; on success, issues new access + refresh token pair
Token Revocation
Logout blacklists the token in a Redis-backed revocation list checked on every request; blacklist entries expire with the token's original TTL
Password Hashing
bcrypt with cost factor 12; salt generated per password
OTP Security
OTPs generated server-side only; stored in Redis (key: otp:{mobile}:{type}, TTL: 5 min); single-use — deleted from Redis on first successful verification; never persisted to MongoDB

15.2 API Security
Measure
Detail
Transport
TLS 1.3 enforced on all endpoints; HTTP redirected to HTTPS; HSTS header set
Rate Limiting
Auth endpoints: 10 attempts / 15 min per IP. OTP request: 3 per mobile per hour. All other endpoints: 300 req/min per authenticated user.
Input Validation
Joi schema validation on all request bodies server-side; mobile number format enforced; file uploads restricted by MIME type and size (max 10 MB per file)
Security Headers
Helmet.js: X-Frame-Options: DENY, Content-Security-Policy, X-Content-Type-Options: nosniff, Referrer-Policy: no-referrer
Admin Namespace
All /api/admin/* routes protected by verifyAdminToken middleware; Admin JWT stored only in httpOnly cookie; no Admin routes reachable from mobile app
CORS
CORS origin whitelist: mobile app bundle IDs and admin web domain only; all other origins rejected with 403
Payment Security
Razorpay webhook signatures verified using HMAC-SHA256 before any payment state change; no payment state changed without a verified webhook event
File Upload
KYC documents stored in private cloud storage (S3-compatible); pre-signed URLs with 15-minute expiry for admin viewing; not publicly accessible

15.3 Data Privacy
Customer mobile numbers are never exposed to Workers (only first name and rating shown)
Worker GPS coordinates broadcast only to the specific Customer whose job is active — not to other users or admins in real-time
Soft-delete: deleting an account anonymises PII fields (name, mobile, email replaced with hashed identifiers) while retaining transaction records for financial audit compliance
KYC document URLs use short-lived pre-signed tokens; documents are never publicly indexed
Audit log entries are immutable — no delete API exists; retained for 12 months for regulatory compliance
